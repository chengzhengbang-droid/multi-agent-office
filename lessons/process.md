### 2026-09-04 · 教训记录从一个文件拆成一个目录，并接上闸门

**背景**
用户指出两件事：教训全写在一个 `LESSONS.md` 里，而教训本身是分维度的（前端的坑对
改事件投影的人没用）；以及"每次改完代码都要更新它"写在约定里，但实际有相当一部分
改动没写。

**教训**

1. **一个只增不减的单文件，最终会因为"翻不动"而失效。**
   它不是被删掉的，是被跳过的：想查前端的坑要先滑过六条协作机制的规矩，
   于是下一次干脆不查了。按维度拆卷之后，读的成本回到"打开一页"，
   写的成本也回到"往一页的头上加一条"。
   代价是多了一个"该放哪一卷"的判断，所以 [README](README.md) 里必须有路由表，
   并且明说按"下一个人在改什么时会需要它"来放，不是按这次动了哪些文件。
   横跨两卷的教训只在一卷写正文、另一卷留指针——复制两份，它们会各自演化然后互相矛盾。

2. **写在约定里的动作，不会自己发生。**（→ [规矩 7](rules.md#7-措辞改不动的事情用机制去改)）
   这是规矩 7 的第二次出现，第一次是审核里的"别为了显得严谨而挑刺"。
   两次的形状一样：一句正确的话，对上一个把它的成本设为零的机制，输的总是那句话。
   所以这次没有再去改措辞，而是把它接进 `pnpm run check` ——
   改了代码却没在 `lessons/` 里留下条目，类型检查那一步就是红的，
   跟少写一个分号一样过不去。CI 在 PR 上跑同一道闸门，忘了写的人在合并前会被拦住。

3. **闸门必须给"这次真的没教训"留一条出口，而且这条出口要收费。**
   （→ [规矩 2](rules.md#2-门禁的成本加在放行一侧不加在怀疑一侧)）
   不留出口，跟着已有模式加一个字段的改动会被逼出一条流水账，
   而流水账正是这个文件最怕的东西。但出口如果免费（比如允许空着不写），
   "这次真的没有"和"忘了写"在记录上就长得一模一样，闸门等于没有。
   所以出口是一条显式的 `无教训 · <一句话为什么>` 记录：便宜，但不是零，
   而且它出现在 diff 里，审核者能看见你做过这个判断。
   闸门专门拒绝 `无教训 · 无` 这种应付——理由太短就不算给过理由。

4. **判断逻辑和 git 管道要分开，否则这道闸门自己没法被测。**
   `lessons-guard.ts` 只吃"改了哪些路径 + lessons 新增了哪些标题"，返回裁决，纯函数；
   `lessons-check.ts` 负责跟 git 说话。于是闸门的每条规则都有单元测试，
   而不是只能靠"在本仓库跑一遍看红不红"来验证。

**以后怎么做**

- 发现某条约定"大家总是忘"，不要再写一遍、写得更大声；去找它接得上的那个机制入口
  （`check`、测试、CI、类型），把忘记的成本从零变成红色。
- 给任何强制项设计逃生口时，先问"用逃生口和正常路径，从记录上分得出来吗"。
  分不出来，这个逃生口就把强制项废了。
- 拆分文档结构时，把"该放哪"的判断成本也算进去，并在索引里替下一个人把它答完。
