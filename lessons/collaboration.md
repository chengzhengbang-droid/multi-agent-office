**适用范围**：`src/core/collaboration*.ts`、`review-convergence.ts`、`reviewer-routing.ts`、
`approval-index.ts` —— 球权、送审、异议收敛、闸门、以及"什么时候该叫人"。

## 变更日志

新的写在最上面。

### 2026-09-04 · 协商轮里也要能问人：互斥前置卡死了唯一的出口

**背景**
用户观察到：审核者提出"这个得跟用户确认"之后，执行 Agent 并不去问用户。
查下来是两件事叠在一起，而只有一件是模型的问题。

**教训**

1. **一条前置条件的适用范围，要跟着它防的那个失败一起看，不能只看它自己是否成立。**
   `request_clarification` 拒绝"已经动过工作区"的 run，防的是"边做边问、拿提问
   给半成品开脱"，这在首轮完全正确。但同一条判断被原样套到审核协商轮上就成了死角：
   协商轮的作者本来就是先把能改的异议改掉，才撞上一条只有人能定的——它必然已经写过了。
   于是那条通路在最需要它的时候永远关着，模型剩下的唯一选择是猜一个交上去，
   而"猜一个交上去"正是审核门存在的理由。
   写这类互斥前置时要问一句：**它在哪个阶段成立？换个阶段这个失败还在不在？**

2. **现有测试只覆盖了畅通的那一半，所以缺口一直没被看见。**
   `plan-mode.test.ts` 里"协商轮发现人类决策"的测试是过的——因为计划模式的协商轮
   强制只读，永远不会产生 write effect，正好绕开了那条前置。verify（可写）那一半
   从来没被测过。一条按 `accessMode` 分叉的规则，只测了只读那一支，等于没测。

3. **平台读不出来的意图，就得给审核者一条机械判据，而不是一句期望。**
   （→ [规矩 7](rules.md#7-措辞改不动的事情用机制去改)）
   审核者写"请与用户确认 X"却不标 `kind: "question"`，平台看到的只是一条普通异议，
   照常派回给作者去争论，想问的那个人根本不会收到。原来的简报说的是
   "只有讨论不出结果时才用 question"——一句要模型自己判断"讨论得出来吗"的话。
   改成可机械自查的形式：**你写的句子里如果出现"让作者去和人确认/对齐"，它就是 question。**

**以后怎么做**

- 给工具加互斥前置时，把 run 的阶段（首轮 / 协商轮、只读 / 可写）当成前置的一部分显式写出来，
  并且为每个分支各写一个测试。只测宽松的那一支不算测过。
- 判断"是不是该叫人"的通路，任何一处拒绝都要能回答：被拒之后，Agent 还剩什么选择？
  如果剩下的只有"猜"，那这条拒绝就是错的。
- 要审核者报一个平台无法复核的字段（severity、kind）时，简报里给的必须是一条
  照着句子就能自查的判据，不是一条要它先做一次判断才能用的定义。

### 2026-09-03 · `04fd933` · 用停滞判据取代轮数上限

**背景**
用户反馈：几乎每个任务最后都要人工介入，而且理由清一色是"审核轮数用完"。
本意是"分歧很大才找人"，实际变成"聊够两轮就找人"。

**教训**

1. **把上限当判据用，会让这个信号自我毁灭。**（→ [规矩 1](rules.md#1-上限不是判据)）
   `max-rounds` 一开始看着很合理：谈不拢就找人嘛。但两个"差一轮就能谈拢"的 Agent
   和两个"卡在同一堵墙上"的 Agent，走的是同一扇门。事件日志里全是 `max-rounds`，
   于是"需要人工介入"这个信号什么都不再说明。
   诊断的时候差点去调轮数上限（2 → 4）就收工——那只会把问题推迟一轮，不会解决它。
   真正要换的是**判据本身**：从"还能谈几轮"换成"这一轮谈动了没有"。

2. **一个二值的裁决字段，会把所有强度的意见压成同一档。**
   `changes-requested` 既表示"这不能上线"，也表示"这个变量名不好"，
   于是审核者的每一次挑剔都在消耗协商预算。加 `severity` 之前，
   任何"让审核者别太挑"的提示词努力都是在跟机制对抗
   （→ [规矩 7](rules.md#7-措辞改不动的事情用机制去改)）。

3. **有些异议不该在 Agent 之间消化。**
   审核者说"原始任务没说超时后该重试还是失败"——这不是缺陷，是需求缺口。
   再谈十轮也只会得到一个论证更漂亮的猜测。这类要立刻抬给人，
   而且抬上去的应该是**那个问题本身**，不是"我们没谈拢"。
   这一条同时说明：找人不等于失败，早点找对人反而更省。

4. **模糊匹配的阈值，要按"错哪一边代价更大"来定，不是按准确率。**
   判断"是不是同一条异议"用的是措辞重合度，必然会有误判。
   误判成"同一条"→ 提前叫人（正是要消除的毛病）；漏判 → 多走一轮（旧行为，可接受）。
   所以阈值取高（0.6 / 0.85），宁漏勿误。这个取舍写进了代码注释，
   否则下一个人看到"准确率不高"会想当然地把它调低。

**以后怎么做**

- 加任何"最多 N 次"的限制之前，先问：N 用完的时候，**发生了什么事实**？
  如果答不上来，这个限制就不该直接接到用户可见的结论上。
- 给裁决类字段加维度（严重度、置信度、可逆性）之前，先看它现在是不是把不同强度的
  东西压成了一档——通常是。
- 改完这类"什么时候叫人"的逻辑，去数一遍：改之前多少条路径通向人、改之后多少条，
  以及每条路径能不能对人说出一句有信息量的话。

**遗留的差距**（自己记着，不是借口）

- 严重度由审核者自己申报，平台不复核。理论上它可以把 nit 标成 blocking 硬卡，
  目前只靠提示词约束。要机制化就得引入按风险轴选验证深度，没做。
- "同一条异议"是措辞重合度这一条机械近似，不是对 failure mode 的语义判断。
  clowder 那边是 Agent 自己判同型，本项目没有那个判断面。
